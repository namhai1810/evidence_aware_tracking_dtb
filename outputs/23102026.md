# Evidence-Aware Tracking Report — HIVE v2

> Report scope: all completed experiments through **HIVE v2**, before HSV bridge similarity was added as a direct model input. Results from the currently running HIVE v3 + HSV training are intentionally excluded.

## 1. Objective and main result

The proposed system targets bandwidth-efficient tracking. An edge device continuously processes a low-resolution (LR) stream at `512×120`. When identity evidence becomes ambiguous, the system selects a valuable historical frame, retrieves its original/high-resolution (HR) `2048×480` version, and uses it as additional identity evidence.

The current experiment isolates **historical frame retrieval after an ID switch is already known**. HIVE v2 receives only LR evidence and ranks up to 20 frames from the five seconds preceding the switch. On four completely held-out videos, HIVE selected a correct frame at rank one for `58/92` events: **Success@1 = 63.04%**. This exceeds the nearest-frame baseline at `27.17%` and the original LR proposal order at `52.17%`.

## 2. YOLO and tracker baselines on QuadTrack

### 2.1 Experimental setup

- Dataset: 17 QuadTrack train videos, sequences `0015`–`0031`, containing 90,763 GT person instances.
- Detector: YOLO11l, person class, confidence `0.20`, NMS IoU `0.70`.
- LR stream: physical input `512×120`, detector `imgsz=512`.
- Original/HR stream: physical input `2048×480`, detector `imgsz=960`.
- Evaluation: Hungarian prediction-to-GT matching at IoU `≥ 0.50`, micro-averaged over all videos.

| Input / tracker | Precision | Recall | F1 | MOTA | IDF1 | IDSW | TP | FP | FN |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 512×120 / ByteTrack | **0.833** | 0.325 | 0.468 | 0.246 | 0.303 | 1,243 | 29,507 | **5,912** | 61,256 |
| 512×120 / BoT-SORT + ReID | 0.818 | 0.339 | 0.480 | 0.253 | 0.353 | **925** | 30,794 | 6,861 | 59,969 |
| 2048×480 / ByteTrack | 0.762 | 0.476 | 0.586 | **0.306** | 0.398 | 1,967 | 43,241 | 13,483 | 47,522 |
| 2048×480 / BoT-SORT + ReID | 0.741 | **0.486** | **0.587** | 0.298 | **0.419** | 1,657 | **44,155** | 15,437 | **46,608** |

At `512×120`, replacing ByteTrack with BoT-SORT + ReID reduced IDSW from `1,243` to `925` (-318; -25.6%) and increased IDF1 from `0.303` to `0.353`. This comparison covers two complete trackers; it is not an appearance-ReID-only ablation.

The lower absolute IDSW count at LR does not mean that LR tracking is better than HR tracking. LR recall is only `0.339`, compared with `0.486` at HR. Many difficult people are missed entirely, so no detection or track remains from which a counted identity switch could arise.

## 3. YOLO + ByteTrack failure cases

For the `512×120 / YOLO11l + ByteTrack` baseline, the evaluator logged:

| Failure statistic | Count |
|---|---:|
| Unique incorrect frames | 8,195 |
| Frames with at least one FN | 8,030 |
| Frames with at least one FP | 3,708 |
| Frames with at least one ID switch | 1,130 |
| Total identity switches | 1,243 |

A frame may belong to several categories simultaneously, so these frame counts must not be summed. The principal failure modes are:

1. **False negative or detection miss:** a person is too small at LR, blurred, occluded, or below the confidence threshold. A tracker cannot preserve an identity without an observation.
2. **False positive:** background or an inaccurate box is classified as a person, increasing FP and potentially creating a false track.
3. **Identity switch:** people cross or stand close together, a person disappears and returns, or the bounding box changes sharply; motion/IoU association assigns a GT identity to another predicted ID.
4. **Track fragmentation:** detections disappear for several frames and the old track terminates. When the person returns, the tracker creates a new ID. Some fragments become counted ID switches when the GT identity is matched again.

HIVE currently targets failure mode 3 and part of failure mode 4 by retrieving historical identity evidence. It does **not** recover an undetected person, remove false positives, or decide by itself when retrieval should be triggered.

## 4. Scope of the current retrieval task

The ranking dataset does not directly use ByteTrack's 1,243 switches. After establishing the baseline, BoT-SORT + ReID was used to reduce initial identity noise. Its **925 GT-confirmed ID-switch events** in the `512×120` stream became the starting points for retrieval.

For a switch at frame `T`, the task is:

> Among LR observations from `T−1` back to `T−150`—the preceding 0–5 seconds at 30 FPS—which frame should be retrieved in its original `2048×480` form to provide evidence connecting the old track with the current target?

The model sees only LR crops when making this decision. Once a frame is selected, its frame index can be used to request the corresponding original image from the edge device. The system therefore does not need to transfer the entire HR history before ranking.

### Included in the current experiment

- The event is already known to be an ID switch.
- Old-track history, a target crop, and historical candidate detections are available.
- The ranker selects a historical frame whose detection belongs to the switch identity.

### Deferred to later stages

- An online trigger that determines whether a normal frame is ambiguous or contains a switch.
- Events for which no positive candidate exists in the candidate pool.
- Actual reassociation or merging of the old and new predicted IDs.
- Tracking replay after merging to remeasure MOTA, IDF1, IDSW, and HOTA.
- Normal/non-switch events. Current negatives are wrong candidates inside known-switch events, not “no-switch” frames.

## 5. HIVE history-ranking dataset v2

### 5.1 LR-only candidate construction

1. Preserve all 925 GT-confirmed switch events and the existing video-level split.
2. For each event, search the complete interval `T−150 … T−1`. The closest observation is approximately 0 seconds before the event and the farthest is 5 seconds before it.
3. Resize the **complete panorama** from `2048×480` to `512×120`, then scale the bounding box and crop the person from the LR frame. An HR person crop is never created and then resized to imitate LR.
4. Build an LR-only proposal descriptor from a `16×8` HSV histogram plus color mean and standard deviation.
5. Retain the strongest LR detection per frame, then select at most 20 candidates per event through three routes:
   - 10 appearance-hard candidates;
   - 5 recent candidates;
   - 5 temporally diverse candidates;
   - preferred spacing of at least three frames, followed by appearance-fill if necessary.
6. **Freeze the candidate pool before reading labels.** Only afterward, Hungarian-match LR detections to GT at IoU `≥ 0.50` and assign supervision labels.

No HR detection, HR crop, or HR ReID embedding is used to construct the v2 candidate pool. GT is joined only after candidate selection for offline supervision.

### 5.2 Positive and negative candidates

- **Positive:** the LR candidate detection is Hungarian-matched to the switch event's `gt_id`.
- **Wrong-identity negative:** the candidate is matched to another person.
- **Unmatched-detection negative:** the candidate matches no GT instance at IoU `≥ 0.50`.

| Full-dataset component | Count | Rate |
|---|---:|---:|
| Switch events | 925 | 100% |
| Candidate pairs | 18,355 | — |
| Positive pairs | 5,725 | 31.19% of pairs |
| Negative pairs | 12,630 | 68.81% of pairs |
| Wrong-identity negatives | 8,777 | 69.49% of negatives |
| Unmatched-detection negatives | 3,853 | 30.51% of negatives |
| Events with at least one positive | 813 | 87.89% of events |
| Events without a positive | 112 | 12.11% of events |

Oracle coverage of `87.89%` means that the candidate pool contains at least one valid answer for 813/925 events. It is an upper bound for any ranker restricted to this pool, not a model accuracy result.

### 5.3 Video-disjoint split and leakage control

| Split | Videos | Sequences | Events | Candidate pairs | Positive | Negative | Oracle coverage |
|---|---:|---|---:|---:|---:|---:|---:|
| Train | 10 | 0015, 0018, 0020, 0021, 0022, 0023, 0024, 0026, 0027, 0029 | 757 | 14,997 | 4,610 | 10,387 | 87.85% |
| Validation | 3 | 0019, 0028, 0030 | 76 | 1,518 | 578 | 940 | 89.47% |
| Held-out test | 4 | 0016, 0017, 0025, 0031 | 92 | 1,840 | 537 | 1,303 | 86.96% |

Leakage audit: **PASS**.

- No videos are shared among train, validation, and test.
- No events overlap across splits.
- No candidate source frames overlap across splits.
- Candidate mining occurs independently within each video's history.
- `train.py` never loads the test manifest; checkpoint selection uses validation Success@1.

The held-out test has now been inspected once for final reporting. Subsequent model changes, including HIVE v3 + HSV, must be selected using validation results rather than repeatedly tuned against this test set.

## 6. HIVE v2 inputs, architecture, and output

### 6.1 Online inputs for one event

- Up to five LR crops from the old track.
- One LR target crop at the switch frame.
- Up to 20 LR candidate crops from the preceding five seconds.
- Up to 30 frames of competing-track history when `lr_new_pred_id` is available.
- Three temporal metadata values per candidate: `age_norm`, `age_squared`, and `log_age`.

Integer track IDs, GT identity, labels, HR images, HR confidence, proposal rank, and HR-ReID similarity are **not model inputs**.

HSV has two distinct roles that must not be conflated:

- The v2 dataset builder uses an LR-only HSV descriptor for **offline candidate proposal**.
- HIVE v2 does **not** receive HSV similarity or the proposal score as a model feature.
- Concatenating three HSV bridge features into the ranking head belongs to HIVE v3 and is outside this report.

### 6.2 Architecture

1. `TinyAppearanceEncoder`: a shared depthwise-separable CNN producing a 64-dimensional appearance embedding for old, target, and candidate crops.
2. `MaskedAttentionAggregator`: target-conditioned aggregation of old-track and competing-track history.
3. `CandidateRelationEncoder`: difference, product, and cosine relations among the old track, target, and candidate.
4. `CompetingHypothesisEncoder`: comparison between each candidate and the competing predicted ID's LR history.
5. Metadata encoder: a small MLP for temporal information.
6. Ranking head: one utility logit per candidate; logits are sorted within the event to produce the final ranking.

The `hive_full` model contains **146,251 trainable parameters**.

### 6.3 Training objective

```text
L = BCEWithLogits(candidate correctness)
  + 0.5 × event-normalized RankNet(positive > negative)
```

BCE learns candidate correctness. RankNet compares every positive-negative pair within the same event and encourages the positive candidate to receive the larger score. Events without a positive still contribute to BCE but cannot contribute a valid pairwise ranking term.

## 7. HIVE v2 training behavior

Main settings: seed 42, deterministic execution, AdamW, learning rate `1e−3`, weight decay `2e−4`, batch size 8, AMP, cosine scheduler, dropout `0.2`, at most 100 epochs, and early-stopping patience 10.

The best checkpoint was selected at **epoch 3**:

| Epoch | Train loss | Validation loss | Validation Success@1 | Validation MRR | Validation NDCG@5 |
|---:|---:|---:|---:|---:|---:|
| 1 | 1.2184 | 1.1746 | 60.53% | 69.76% | 60.93% |
| 2 | 1.0422 | **1.0292** | 63.16% | 70.53% | 61.89% |
| **3** | **0.9025** | 1.0934 | **64.47%** | **71.28%** | **62.61%** |
| 13 | 0.4785 | 1.4333 | 52.63% | 64.22% | 56.51% |

After epoch 3, training loss continued to decrease while validation loss increased and validation Success@1 deteriorated. This is clear overfitting after epoch 3. Early stopping behaved correctly and retained epoch 3 as `best.pt`.

The held-out test contains only videos `0016, 0017, 0025, 0031`: 92 events and 1,840 candidates.

| Candidate recall | 86.59% |
| Candidate F1 | 63.92% |

| Oracle candidate coverage | 86.96% (80/92) |

### 8.2 Frame-selection comparison

| Selection method | Correct top-1 | Success@1 | Difference from HIVE |
|---|---:|---:|---:|
| Nearest historical frame | 25/92 | 27.17% | HIVE +35.87 points and +33 events |
| Original LR HSV proposal order | 48/92 | 52.17% | HIVE +10.87 points and +10 events |
| **HIVE v2, epoch 3** | **58/92** | **63.04%** | — |
| GT oracle within the candidate pool | 80/92 | 86.96% | 22-event remaining gap |

HIVE reaches `2.32×` the Success@1 of the nearest-frame heuristic. Of the 80 events for which a correct answer exists in the candidate pool, HIVE places a positive at rank one for 58 and fails at rank one for 22. The remaining 12 test events contain no positive candidate, so no reranker restricted to this pool can solve them.

### 8.3 Inference speed

| Component | Result |
|---|---:|
| HIVE model latency | 0.815 ms/event |
| Encoder latency | 0.734 ms/event |
| Scorer latency | 0.004 ms/candidate |
| Estimated model-only throughput | approximately 1,226 events/s |

Evaluator throughput includes image loading, resizing/cropping, batching, metric computation, and output serialization. It is not the FPS of the complete YOLO + tracker system. The LR HSV proposal cost was not benchmarked online because candidate order was materialized during dataset construction.

## 9. What improved—and what cannot yet be claimed

### Directly measured improvements

- BoT-SORT + ReID reduced LR IDSW from 1,243 to 925 and increased IDF1 from 0.303 to 0.353 relative to ByteTrack.
- HIVE v2 improved **frame-selection Success@1** from 27.17% for nearest-frame selection and 52.17% for the original proposal order to 63.04% on held-out videos.
- The LR-only test candidate pool reached 86.96% oracle coverage.
- Video-disjoint splitting and all implemented leakage checks passed.

### Claims that require tracking replay

The `58/92` correct top-one result cannot be reported as “58 identity switches fixed,” and it does not define a new MOTA, IDF1, or IDSW value. A GT-positive candidate is useful retrieval evidence, but demonstrating improved tracking requires the following complete path:

1. Fetch the selected frame at HR.
2. Extract identity evidence from the HR observation.
3. Decide whether and how to reassociate or merge the old and new IDs.
4. Replay the tracker or modify the MOT output consistently.
5. Run the tracking evaluator again to measure MOTA, IDF1, IDSW, and HOTA.

## Conclusion

HIVE v2 demonstrates that a lightweight ranker using only LR evidence can select useful historical frames substantially better than a temporal heuristic or the original proposal order, without reading an HR image before making the selection. The current result validates **historical frame selection**, not yet end-to-end tracking correction. The decisive next evaluation is to connect the top-ranked frame to identity reassociation and tracking replay, then directly measure the reduction in identity switches and the change in IDF1 and MOTA.
